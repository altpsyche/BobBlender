## Where things stand (context)

The BobBlenderTools extension restructure P0–P7 is DONE and uncommitted on this branch:
- `blender/extensions/bob_blender_tools/` is the self-contained product: `core/` (builders +
  `core/heightfields` the single-source terrain compute + `core/assets` the pack resolver), `ui/`
  (panels + `helpers`), `bridge/` (the live socket `server`), `compute.py` (GPU/CPU delivery),
  `assets/` (bundled block-out pack), thin `__init__.py`. Every intra-package import is relative;
  a CI lint (`tools/scripts/check_selfimports.py`) enforces it.
- `tools/` is the venv toolchain (Python 3.14, no bpy): `bobtools/mcp/` (the agent bus),
  repo/pipeline utils, `_hfpath.py`/`hf_cli.py` (locate + run the extension's compute from the
  venv). `docs/API.md` (op table generated by `tools/scripts/gen_api_docs.py`), `docs/ARCHITECTURE.md`,
  `docs/RESTRUCTURE-PLAN.md` describe it all.
- Verified working: 71 pytest green; packaged zip installs and runs standalone for artist features;
  terrain bakes in-process (GPU via `compute.Enable Compute`, with a dev-venv host-hop fallback for
  the Steam-sandbox + CUDA-13 case).

**The gap this task closes:** artist features (World/Biome/Terrain/Paths/Scatter/Shaders/Atmosphere)
work out of the box from the zip, but **MCP agent authoring is not self-contained** — it needs the
cloned repo + `tools/` venv. And a few stale comments in `core/` still imply a venv dependency that
no longer exists.

## Current MCP wiring (facts to build on)

Two halves:
- **Blender side (shipped in the extension):** `bridge/server.py` — a localhost socket server that
  applies whitelisted `core` ops on Blender's main thread. Panel: Advanced → Start/Stop, Reload
  Builders. Self-contained, no `tools/` import. Port from `bob.toml` `[bridge] port = 9876` or
  `$BOB_BRIDGE_PORT`.
- **Agent side (venv-only, NOT shipped):** `tools/bobtools/mcp/`:
  - `mcp_server.py` — the stdio MCP server (`bob-mcp`, FastMCP "bobblendermcp"). Tools:
    `list_projects`, `create_project`, `list_library_assets`, `build`, `build_live`,
    `bake_heightfield`, `build_live` etc.
  - `contracts.py` — the Pydantic op vocabulary (validated here).
  - `executor.py` — headless executor: spawns Blender + `blender/runners/headless_build.py` for
    `build`.
  - `bridge.py` — live executor: sends ops to the running Blender via the socket for `build_live`.
  - `config.py` — resolves Blender binary, bridge host/port, and **repo paths** (`projects/`,
    `library/`) — this is where the repo-coupling lives.
- `.mcp.json` registers it as: `uv run --project ${CLAUDE_PROJECT_DIR}/tools --extra mcp bob-mcp`
  (stdio). So today it REQUIRES: the repo checkout, `uv`, the `tools` venv, and repo-relative paths.

## Goal 1 — make MCP self-contained (+ how-tos)

**Definition of done:** an agent (Claude Code, or any MCP client) can drive Blender over MCP
WITHOUT cloning this repo — install the extension zip, install/run the MCP server via one
documented command, point the client at it, and `build_live` / `build` work against arbitrary
project + asset-pack folders (not hardcoded repo paths).

Decide the approach (recommend + confirm before building; the two hard parts are packaging and the
headless `build` path):

1. **Decouple repo paths.** Audit `bobtools/config.py` (and `mcp_server.py`, `scaffold.py`,
   `executor.py`) for assumptions that `projects/`, `library/`, and the repo root exist. Replace
   with configuration: `$BOB_PROJECTS`, `$BOB_ASSET_PACKS` (already read by `core/assets`), a
   working dir, or a small user config file. The server must run pointed at a user's own folders.
2. **Packaging — make `bob-mcp` installable without the repo.** Options:
   - `uvx`/`pipx`-run a published `bobtools` (or a slimmer `bobblendermcp`) package, so `.mcp.json`
     becomes `uvx bobblendermcp` with no `--project` repo path. Requires publishing to PyPI or a
     git ref.
   - Ship a wheel with the extension and document a `pipx install ./wheel` / `uv tool install`.
   - Whichever: the deps are `mcp>=1.2` + `pydantic>=2` only (light). No bpy, no numpy needed on
     the agent side.
3. **The headless `build` path is the hard one.** `executor.py` spawns Blender with
   `blender/runners/headless_build.py`, which is in the repo, NOT in the extension zip. For a
   standalone install decide one of: (a) move the headless entry INTO the extension (e.g.
   `core/headless.py` or a `runners/` inside the extension) so a `blender --python` invocation can
   import the installed `bl_ext...bob_blender_tools.core.dispatch`; (b) have the MCP server locate
   the installed extension and drive it; (c) scope self-contained MCP to `build_live` only (live
   session) for v1 and keep headless `build` dev-only. `build_live` needs only the socket + the
   running Blender, so it is the easier win — but confirm the intended scope with the user.
4. **Blender-binary discovery** already exists (`config.blender_binary`: `$BOB_BLENDER`, known
   installs, PATH) — reuse it; make sure it works with no repo.

**How-tos (write `docs/MCP.md`, and link it from README + ARCHITECTURE):**
- Install the extension (from the built zip: Preferences → Get Extensions → Install from Disk).
- Enable the bridge (Advanced → Start, or autostart pref) — note autostart defaults OFF.
- Install + run the MCP server (the chosen one-liner) and the `.mcp.json` snippet to paste.
- Connect from Claude Code (approve the server; `/mcp reconnect bobblendermcp`).
- The two-sided reload rules (already in ARCHITECTURE): recipe body change → Reload Builders;
  op-contract change → reconnect the MCP server.
- Pointing at your own project/asset folders (the env vars from step 1).
- Troubleshooting: bridge not running, port in use, server not connecting, wrong Blender binary.
